关键参数与背后的取舍 全部回代码核实

环节关键参数为什么这么定
调度Beat 每 30 分钟一轮；每个用户再按自己的评估间隔节流（默认 20 分钟，下限 5 分钟） 抓取和评分分在不同队列，互不阻塞；打开看板会顺手投递一次匹配，但有双重节流，刷新页面打不爆队列
评分缓存prompt_signature = sha256(prompt + 阈值 + 分类 + 关键词) 用户改一个字，签名就变，历史文章自动重新进候选队列 —— 不需要手工触发全量重算
去重余弦 ≥ 0.92 判为重复；判重的文章也写一行分数为 0 的记录 这行记录带着当前签名，下一轮候选查询直接把它排除，重复文章不会被反复捞回来重算
聚类48 小时窗口、余弦 ≥ 0.82（用户可调），按分数降序贪心归簇 因为按分数降序，簇代表天然就是簇内最高分那篇；看板和邮件都只发代表，同一事件不会刷屏
容错评分失败、落库失败、翻译失败、聚类失败各自隔离 一条脏数据只跳过它自己，不影响这个用户这一轮的其余文章；有专门的回归测试覆盖
去重和聚类共用同一份向量缓存，聚类那一步不再调模型 —— 存的是归一化向量，点积就是余弦。

个性化看板

  • 三栏可拖拽：筛选 / 列表 / AI 对话
  • 全文检索走 PostgreSQL 原生索引，标题 A 权重、摘要 B 权重，命中不足自动降级
  • 可按来源、关键词、作者、我的分类、日期、关注的同事六个维度筛
  • 只显示簇代表，相似的收在「+N 相似」里
  • 右侧 AI 对话可带最多 5 篇文章当上下文
  • 排序可选时间或分数，每页 20 / 50 / 100 条
  • 打开页面时若距上次匹配超过间隔，自动补投一次匹配任务，带双重节流

邮件摘要

  • 取数三段式：本人匹配 → 关注同事的匹配 → 订阅源内最新兜底，兜底严格限定在自己人的源里
  • 三重去重：ID、归一化 URL、标题字符集相似度 ≥ 0.45
  • 日 / 周 / 月 / 单次四种频率，下次发送时间在用户时区里算
  • 月历视图 + 编排面板 + 发送历史快照
  • 可自定义主题、Logo、三个主题色，条数 1–200、时间窗 1–720 小时
  • 两档权限：有完整权限才能发给收件人列表，其余降级为只发给自己
  • 支持跳过下一次、用冻结快照发送，单次计划发完自动停用

订阅与反馈

  • 粘任意网站链接就能订：解析不出 RSS 就自动调 RSS.app 生成一个
  • 也能按关键词订，或者直接关注同事的新闻流
  • 最后一个订阅者退订时，本地和远端的 feed 一起删，省外部服务配额
  • 订阅中心按管理员编排的分类批量点选

【工程亮点】六个踩过坑才定下来的做法
都是线上出过问题、改完有明确收益的地方，不是设计文档里的理想方案。

① 抓取热路径零数据库写

  • 老实现是抓一篇写一篇，一条数据库连接被几十篇文章的慢网络占住
  • 改成解析、抓正文、内存加工三段全程不碰库，最后 50 条一个事务落库
  • 事务窗口从「整个源的抓取时长」压缩到「一次批写」；整批失败自动降级逐条
  • 已经有正文的文章直接跳过抓取；源自报的构建时间没变就一个字节都不写

② 长连接的连接与心跳

  • 流式响应返回前先把数据库连接还回池子 —— 一条连接被十几分钟的 SSE 占住，池子扛不住
  • 生产者线程 + 队列，10 秒拿不到事件就补一个心跳，防代理和 nginx 掐断
  • 响应头关掉 nginx 缓冲，前端配两次自动重连
  • 评分线程进出各做一次连接回收 —— LLM 调用是分钟级的，不主动关会把池子吃穿

③ gevent + psycogreen

  • gunicorn 用 gevent，每进程 200 个协程扛 LLM 转发这种长 IO
  • 但 psycopg2 默认是阻塞的，一条数据库查询就能把整个进程的协程池卡死
  • 在 post_fork 钩子里打补丁，把等待交回调度器 —— 不打这个补丁等于白用协程
  • 超时设到 1800 秒，因为深度研究那条流本来就要跑十几分钟

④ 后台慢查询重写

  • 订阅源列表原来每行挂两个 COUNT 子查询打在巨大的新闻表上，一页 60 行
  • 改成两条 GROUP BY 一次算完 + 10 分钟缓存
  • 新闻列表原来一条查询里两个 COUNT(DISTINCT)，PostgreSQL 要建笛卡尔积临时表，直接把磁盘写满；改成两个独立子查询避开 join

⑤ 模型注册表单点收口

  • 24 个模型注册项的 id、端点、密钥、走不走代理集中在一个文件
  • 前端配置由它自动生成，加一个本地模型只改这一处
  • 外部模型走代理、120 秒超时；内网模型直连、读超时不设上限 —— 两套客户端策略由注册项自动决定
  • 内网客户端显式不读环境变量，免得被全局代理设置劫持

⑥ 先预检再动线上进程

  • 热重载脚本五个阶段：wsgi 导不进来、有未应用的迁移、JSX 比构建产物新，任一不过就直接退出，老进程原封不动继续服务
  • 重载信号必须打给主进程，打错目标只会杀掉一个 worker
  • Celery 重载完睡 5 秒再数一次进程，少了就报错而不是假装成功
  • 全量重启时静态收集失败即中止，不带着半套静态资源起服务
这六条的共同点：先让系统在出错时不塌，再谈快 —— 单篇失败只跳过单篇，整批失败降级逐条，预检不过就不动线上。

阅读与标注 把个人阅读变成团队资产

  • 共享标注：开启"公开我的笔记"后，同事读同一篇时能在原文位置看到你的划线，并可针对某一条划线开讨论 —— 相当于在文档上做异步共读。
  • 个人笔记面板：本篇的全部划线与批注集中查看、可跳回原文位置。
  • 选中即译：读英文论文时选中一段就地给出中文，反之亦然，不必把内网内容贴到外部工具。
  • 阅读进度：记录读到第几章、百分之多少，换台机器继续读；可加入书架。
  • PDF 双视图：原版按原貌阅读，精读视图支持划线、批注与 AI 引用跳转。

提问与协作

  • 带出处的问答：每句结论后跟一个可点角标，点击跳回原文并高亮，可当场核实 AI 是否如实转述。

  • 相似文档推荐：读完一篇给出相关的其他文档。

组织者 建活动与管过程

  • 两种作品来源：批量上传（按文件名规则自动解析作品名 / 作者 / 工号，人工改过的条目不被覆盖）；或开放成员自主投稿。

断点一：从"看"到"发" 三个原因

  • 看到的是内容列表，不是人。不知道谁在做什么，缺少互动起点。
  • 第一条门槛高。担心写得不好、不确定发在哪、排版耗时。
  • 缺少发布场景。只有"正式内容"的位置，没有"日常记录"的位置。

断点二：从"一次"到"持续" 两个原因

  • 发布后无回响。零回复即等同于"第一次就是最后一次"。
  • 贡献无出口。点赞与下载量只是流水，既不进入个人履历，也不带来实际权益。
由此得出的判断：继续扩展功能无法改善上述五项原因中的任何一项。本轮建设应集中于机制 —— 让人可见、让发布容易、让留存有理由。三条发展路线由此展开。

  • 吸收关系不可逆。B 与 C 都可以作为 A 的组成部分存在，而 A 无法被 B 或 C 承载 —— 只有专栏或只有额度，都不产生人与人的连接。
  • 资产属性不同。专栏的资产是文章，额度的资产是一次性消耗，A 的资产是关系网络，随时间增值且不可复制。
  • 独有优势只在 A 生效。实名与部门信息使"认识同事"成立，这是外部社区无法获得的条件；同事关系本身即是分发网络。
  • 风险可控。A 的主要风险是内容参差与首发顾虑，可通过分区、正向激励与管理员示范缓解；C 的灌水风险则会直接损害内容资产。
对比维度A · 真人社区（建议主线）B · 专家专栏C · 资源挂钩
内容供给方全员，日常记录亦为内容，供给面最宽少数专家，约稿制，供给面最窄被动产生，为获取额度而发布
运营投入中：3–5 名种子活跃者 + 每周一次精选高：需编辑、约稿与排期，断更即失效低：规则自动执行，但需额度池授权
主要风险内容参差；实名环境下首发顾虑与既有严肃社区同质化，且缺少作者储备为获取额度而灌水，并将分享行为交易化
建议定位★ 作为主线作为 A 内的一个栏目作为 A 的放大器
结论：以 A 为主线，B 降级为栏目，C 定位为放大器。三线并行将导致资源分散且互相稀释。

  • 只奖励被他人使用的贡献 —— 回答被采纳、Skill 被安装、文档被收藏、收到致谢；发布条数不计分。此条决定了它不会演变为灌水机制。
